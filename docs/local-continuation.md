# Продолжение работы в локальной Windows-задаче

## Цель

Автоматизировать существующую работу оператора в 1С для Wildberries FBS по трём организациям: Белименко Елена, Белименко Сергей и Нота. Цепочка: загрузка заказов → синхронизация товаров по кабинету → сопоставление недостающих артикулов → повторная загрузка заказов → поставка → сохранение и печать этикеток → передача менеджеру.

Пользователь просит вести работу самостоятельно и разрешил координацию между задачами. При наличии инструментов чтения чатов использовать контекст «Настройка -» и «Определить конфигурацию 1С», не заставляя пользователя пересказывать уже известные сведения. Не утверждать, что между чатами отправлено сообщение, если инструмент отправки недоступен.

## Что уже выполнено

- Репозиторий: `https://github.com/pentagon198513-commits/-.git`.
- Локальная задача «Определить конфигурацию 1С» успешно управляла существующим RDP-сеансом с помощью доступного на ноутбуке навыка управления компьютером.
- По её отчёту: «Управление торговлей, редакция 11», версия **11.4.6.188**; платформа **8.3.27.1688**; установлены расширения, включая работу с маркетплейсами.
- При осмотре данные и настройки базы не изменялись. Окно сведений оставлено открытым, но перед новым действием нужно получить актуальное состояние.
- В `supply_assistant/` реализован отдельный модуль точного сопоставления по артикулу и штрихкоду. Выполнен 31 тест. Это пока локальный компонент без подключения к 1С.
- Пользователь подтвердил: после сохранения соответствия артикула из «сборки» номенклатуре 1С повторная загрузка заказов заполняет название товара. Нужная номенклатура находится по такому же артикулу или штрихкоду.

## Первые действия

1. Проверить текущую рабочую папку, инструкции и существующие изменения. Использовать подходящую существующую копию репозитория; если её нет, создать обычную отдельную папку с клоном. Не перезаписывать чужие файлы. Задачи уже изолированы; отдельный Git worktree без запроса пользователя не нужен.
2. Прочитать доступный в локальной задаче навык управления компьютером и работать его поддерживаемыми инструментами. Получить свежее состояние существующего RDP-окна.
3. Зафиксировать точные названия и версии расширений, относящихся к Wildberries, и найти их документацию или справку. Не выводить наличие API из одной только версии УТ.
4. Найти выбор кабинета и организации. Зафиксировать соответствие трём организациям; не предполагать, что на каждую приходится отдельный кабинет.
5. На существующем заказе с пустым полем товара изучить исходный артикул/штрихкод, раздел «сборка», форму поиска номенклатуры и характеристику товара. Сравнить с существующим заказом с заполненным соответствием.
6. На существующей поставке изучить состав, статусы и доступные действия получения этикеток. Определить формат файлов, место сохранения и доступную печать. Канал передачи менеджеру ещё неизвестен.
7. Сохранить найденные поля и последовательность в документации. Выбрать реализацию через поддерживаемый интерфейс расширения либо управление окнами, исходя из фактов.

Начальный осмотр выполняется на существующих документах. Не запускать обмен, не сохранять соответствия и не создавать поставки лишь ради изучения кнопок. Рабочие заказы для проверочной обработки нельзя выбирать произвольно до определения правил отбора.

## Проверка готового компонента

Из корня репозитория, Python 3.10 или новее:

```sh
python -m unittest discover -s tests -v
python -m supply_assistant examples/matching.json
```

У демонстрации ожидается код завершения `2`: одно соответствие найдено, три строки требуют разбора. Тесты должны завершаться кодом `0`. Сторонних зависимостей нет. Детали входных данных — в [matching.md](matching.md).

## Что ещё не реализовано

Нет адаптера реальных заказов и каталога 1С, сохранения соответствий, создания поставок, получения и печати этикеток или передачи менеджеру. Сначала требуется сопоставить внутренние поля проекта с фактическими данными используемого расширения.

Артикул хранить строкой, учитывать кабинет, организацию и характеристики. Не выбирать первый товар при нескольких совпадениях и не заменять существующие связи по сходству названий. После сохранения связи отдельно проверять повторно загруженный заказ. Не считать локальное предложение сопоставления уже записанным в базу.

Адреса подключения и учётные данные не нужно переносить в исходники или журнал. Для осмотра использовать уже открытый пользователем сеанс.
