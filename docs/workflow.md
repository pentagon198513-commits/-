# Автоматизация поставок: описание процесса

## Что известно

- У пользователя есть доступ к серверу, на котором расположена 1С, и отдельный доступ в 1С. Работа идёт через удалённый рабочий стол Windows.
- Нужно обрабатывать три юрлица: Белименко Елена, Белименко Сергей и Нота. Это рабочие названия из описания пользователя; точные записи в 1С ещё не проверены.
- Заказы из Wildberries (WB) загружаются в 1С. Пользователь подтвердил схему FBS: отправка заказов со своего склада.
- В отчёте локального чата «Определить конфигурацию 1С» от 17 октября 2026 года указаны конфигурация **«Управление торговлей, редакция 11», версия 11.4.6.188**, и платформа **8.3.27.1688**. Локальный исполнитель прочитал окно «О программе» через действующий сеанс RDP.
- В том же отчёте отмечены установленные расширения, включая работу с маркетплейсами. Их точные названия, версии и программные интерфейсы пока не зафиксированы.
- На присланном снимке выбран режим «На сервере 1С:Предприятия»: указаны внутренний адрес кластера и имя информационной базы `UT`. Это клиент-серверное подключение, а не адрес опубликованного веб-клиента. Имя базы само по себе не устанавливает название конфигурации.
- В списке заказов поле товара бывает пустым, при этом количество и цена указаны.
- В 1С есть кнопка синхронизации с Wildberries по выбранному кабинету; по описанию пользователя она синхронизирует товары.
- Для недостающего соответствия пользователь берёт артикул из «сборки», вводит его в 1С, вручную сопоставляет с товаром 1С и сохраняет. После повторной загрузки заказов появляется название товара из 1С. Этот процесс описан пользователем, но ещё не проверен на подключённой системе.
- Пользователь подтвердил, что выбирает номенклатуру 1С по такому же артикулу или штрихкоду.
- Поставки создаются и этикетки получаются в 1С. Нужно печатать и сохранять этикетки и передавать их менеджеру.

## Подтверждённый пользователем процесс сопоставления

1. В 1С выбирается нужный кабинет Wildberries и запускается синхронизация товаров.
2. Для товара без соответствия артикул берётся из «сборки». Точное название раздела и тип артикула пока неизвестны.
3. Артикул вводится в 1С и связывается с нужной номенклатурой 1С.
4. Соответствие сохраняется.
5. Заказы загружаются повторно, после чего поле товара содержит название номенклатуры из 1С.

Пользователь находит целевую номенклатуру по одинаковому артикулу или штрихкоду. Первый программный модуль реализует точный поиск по этим полям с отдельным результатом для неоднозначностей. Названия полей реальной конфигурации и работа с характеристиками ещё требуют проверки.

## Предлагаемый первый рабочий сценарий программы

1. Пользователь выбирает юрлицо и запускает обработку заказов. Правила отбора заказов нужно уточнить по существующему процессу.
2. Программа получает заказы через используемый механизм 1С, использует уже сохранённые соответствия и выявляет строки с пустым товаром.
3. Для нужного кабинета программа запускает синхронизацию товаров и проверяет её завершение. Недостающие соответствия артикула из «сборки» номенклатуре 1С создаются по проверенному правилу выбора товара. Если выбрать товар однозначно невозможно, пользователю показываются исходный артикул и причина, по которой требуется ручной выбор.
4. После сохранения соответствий программа повторно загружает заказы и проверяет, что строки связаны с ожидаемой номенклатурой. Неразрешённые ошибки показываются пользователю; правила частичной обработки заказа нужно согласовать.
5. Программа создаёт поставку через используемый процесс в 1С, связывает её с заказами и соответствующим юрлицом. Конкретные документы, действия и момент отправки данных в Wildberries пока неизвестны.
6. Программа получает этикетки через используемый процесс в 1С и сохраняет их с привязкой к юрлицу, поставке и заказам. Механизм получения этикеток, формат и размеры нужно уточнить.
7. Программа печатает этикетки через доступный принтер и передаёт сохранённые документы менеджеру по согласованному каналу.
8. Пользователь видит результат: какие заказы обработаны, какая поставка создана, где находятся документы и что требует исправления.

Сценарий программы — предложение для обсуждения. Наличие ручных операций в 1С подтверждено пользователем; возможность выполнять их программно ещё не проверена.

## Что определяет способ подключения

В первую очередь нужно выяснить:

- Названия и версии установленных расширений для маркетплейсов, их доработки и доступные интерфейсы обмена. Версии основной конфигурации и платформы уже определены.
- Какие разделы, документы и команды 1С используются для поставок и этикеток.

Название конфигурации и версии установлены локальным исполнителем через окно «О программе». По его отчёту данные и настройки базы при осмотре не редактировались; окно сведений оставлено открытым. Для следующего действия нужно заново проверить фактическое состояние окна.

Для точной реализации потребуется пройти один обычный заказ и один случай, в котором требуется обмен данными. Нужно записать названия разделов, команд, документов и ожидаемый результат каждого шага.

Далее уточняются:

- Соответствие юрлиц организациям, складам и кабинетам маркетплейса. Нельзя предполагать отдельный кабинет для каждого юрлица.
- Точное название кнопки синхронизации, раздела «сборка» и окна сопоставления, а также признаки завершения обмена и сохранения связи.
- Какой именно артикул переносится и в каких полях конфигурации хранятся артикул и штрихкод, по которым пользователь находит номенклатуру. При наличии размеров, цветов или иных характеристик нужно выяснить, как выбирается конкретный вариант товара.
- Правила включения заказов в поставку, ограничения по складам, статусам и срокам.
- Формат этикеток, порядок печати, доступный принтер и место хранения файлов.
- Получатель документов и способ передачи: общая папка, почта, мессенджер или другой канал.
- Режим работы: запуск человеком или расписание.

## Варианты реализации

При наличии поддерживаемых интерфейсов 1С и маркетплейса предпочтительна интеграция через них. Сам факт доступа по логину и паролю не означает наличия API или прав на публикацию сервисов 1С.

Если рабочий процесс доступен только через окна Windows, возможен исполнитель на Windows с доступом к 1С. Для него потребуются проверка рабочего сеанса, устойчивые признаки завершения операций и работа с используемым принтером. Облачная среда разработки сама по себе не предоставляет доступ к окнам удалённого сервера.

Возможен смешанный вариант: часть действий через интерфейсы обмена, часть через установленный клиент. Выбор делается после проверки доступных способов подключения. Локальный модуль сопоставления реализован на Python без сторонних зависимостей; способ подключения и место запуска интеграции пока не выбраны.

## Поведение при повторах и ошибках

- Заказы и документы связываются по идентификаторам вместе с организацией и кабинетом, чтобы данные разных юрлиц не смешивались.
- При сопоставлении используются существующие связи в 1С. Сохранённые связи не заменяются автоматически только из-за сходства названий.
- Переносимый артикул сохраняется как текст без удаления начальных нулей или изменения символов. Тип артикула определяется по фактическому полю в интерфейсе, без предположения о том, что это идентификатор WB или артикул продавца.
- Сохранение связи и повторная загрузка заказов — разные шаги. Успех проверяется по ожидаемой номенклатуре в повторно загруженном заказе, а не только по нажатию кнопки сохранения.
- Повторный запуск проверяет уже созданные документы и поставки.
- После потери связи во время создания документа сначала проверяется результат операции; создание не повторяется вслепую.
- Перед печатью и передачей сверяются соответствие этикеток заказам и состав поставки.
- Для каждого шага фиксируется состояние. Создание поставки, сохранение этикеток, передача задания принтеру и передача менеджеру учитываются отдельно.
- Отправка задания в очередь печати не считается доказательством физической печати. Возможность проверки результата зависит от принтера.
- Ошибка и следующий доступный шаг должны быть понятны пользователю. Пароли и ключи не попадают в журнал.

## Как проверять готовность

После выбора подключения сначала проверяется чтение необходимых данных. Затем на согласованном примере проверяется полный путь заказа до поставки и файлов этикеток.

Отдельные проверки нужны для каждого юрлица, строки с уже существующим соответствием, нового сопоставления с повторной загрузкой заказов, неоднозначного выбора номенклатуры, повторного запуска и потери связи после создания документа. Печать и передачу менеджеру нужно проверить на реальных выбранных устройствах и каналах.

Сейчас подготовлены репозиторий, описание процесса и локальный модуль сопоставления с демонстрационными данными; выполнен 31 тест. Отдельный локальный исполнитель проверил управление существующим RDP-сеансом и прочитал сведения о 1С. Программный обмен, сохранение соответствий, создание поставок, печать и отправка документов ещё не проверены. Формат и границы готового модуля описаны в [matching.md](matching.md).

## Доступы

Пользователь разрешил самостоятельное подключение к серверу или работу через его ноутбук и предпочитает, чтобы исполнитель сам осматривал интерфейс вместо запроса скриншотов. После проверки локального управления дальнейшую работу с интерфейсом следует вести через действующий RDP-сеанс на ноутбуке.

В текущем облачном сеансе нет инструмента управления ноутбуком пользователя. Клиент RDP и графический сеанс не подготовлены. Доступны средства для HTTPS/браузера и SSH, но их наличие не подтверждает, что соответствующий вход разрешён и настроен на сервере 1С. Подключение к серверу ещё не выполнялось.

Пользователь предоставил внешний IP-адрес и подтвердил, что подключается без VPN. Отдельно прислан снимок внутренних параметров базы. Прямую доступность внутреннего кластера из облака нельзя предполагать: проверять его нужно из соответствующей серверной сети. Не нужно просить пользователя повторно разрешать уже разрешённый осмотр.

Последующий снимок заголовка окна удалённого рабочего стола подтвердил нестандартный порт RDP **8889**. Первоначальная проверка стандартного порта 3389 не относилась к фактически используемому подключению.

Первоначально TCP-соединение на подтверждённый порт 8889 завершалось отказом, а CONNECT через облачный HTTPS-прокси — ответом 403. При последующей проверке поведение изменилось: CONNECT стал приниматься с кодом 200. Это ещё не доказывает прохождение RDP.

После CONNECT отправлен штатный начальный пакет X.224/RDP_NEG_REQ с запросом TLS/NLA. Маршрут закрыл соединение до получения полного ответа RDP. Отдельная проверка прямого соединения вне локальной песочницы также завершилась отказом TCP. HTTPS-проба на этом порту завершилась несоответствием имени сертификата; проверка сертификатов не отключалась. Протокольный ответ RDP и экран входа Windows не получены. Эти результаты не подтверждают неисправность сервера. Пароль не передавался ни в одном диагностическом запросе.

Внешний IP добавлен в сетевой список разрешённых адресов черновика среды с сохранением существующих пресетов. Инструмент подтвердил сохранение и необходимость публикации; отдельного подтверждения публикации нет. Наблюдаемое разрешение CONNECT не доказывает, каким способом обновилась работающая среда. Повторять рекомендацию о публикации как достаточном решении для RDP нельзя: для фактического протокола рабочий маршрут пока не найден.

Создан отдельный локальный чат «Определить конфигурацию 1С». По прочитанному отчёту он успешно использовал локальный навык управления компьютером, работал с окном удалённого рабочего стола и прочитал сведения о программе. Это подтверждает возможность управления в локальной задаче, но не предоставляет такие же инструменты текущему облачному чату.

Пользователь явно разрешил координацию между задачами без постоянной передачи сообщений через него. Проверено, что облачный набор инструментов позволяет читать локальный чат, но не содержит отправки сообщений, запуска или передачи задачи в другой чат. Ведение следующих этапов нужно продолжить в локальной задаче по [инструкции](local-continuation.md). Нельзя утверждать, что она уже получила новое задание или выполняет его. Пароль в инструкции передачи задачи не включается.

Логины, пароли, ключи и реальные данные заказов не сохраняются в исходном коде или документации. Секретные значения не запрашиваются в чате. После выбора подключения нужно проверить уже доступные привязки и определить безопасный способ настройки только недостающих доступов.

Проверка доступной конфигурации показала отсутствие пользовательских привязок секретов и параметров сервера. Секреты в настройках этой облачной среды предназначены для подстановки прокси на разрешённых HTTPS-адресах; их нельзя считать источником обычного пароля для локального RDP-клиента. Способ передачи доступа должен соответствовать выбранному протоколу.
